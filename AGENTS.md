# AGENTS.md



## Назначение



Этот файл является главным вводным документом для ChatGPT, других ИИ и разработчиков, работающих над проектом Mikhlink.



Перед началом любой работы необходимо:



1. Прочитать этот файл полностью.

2. Прочитать документацию из папки `docs`.

3. Проверить последние изменения в ветке `main`.

4. Не делать выводов только на основании истории чата.

5. GitHub-репозиторий является главным источником истины.



---



# Что такое Mikhlink



Mikhlink — открытый проект, создаваемый для Windows.



Главная цель проекта — создать максимально надёжную систему для мобильного IRL-стриминга через несколько интернет-соединений одновременно.



Проект создаётся не как учебное приложение и не как демонстрация технологий.



Все архитектурные решения должны приниматься исходя из практической пользы при реальном стриминге.



---



# Главная цель



Конечная цель проекта:



Создать открытую замену рабочей связке Moblin + Moblink для Windows.



При этом проект НЕ является копией Speedify.



Speedify был протестирован автором проекта и не подходит для поставленной задачи.



Главный ориентир — практическое поведение Moblink/Moblin при реальном мобильном IRL-стриминге.



---



# Основные принципы разработки



При разработке соблюдать следующие правила.



- После каждого этапа проект должен собираться.

- Не писать код "на будущее", пока он реально не нужен.

- Не добавлять зависимости без необходимости.

- Все серьёзные архитектурные решения документировать.

- Любое утверждение о работоспособности должно подтверждаться реальной проверкой.

- Простое решение предпочтительнее сложного, если они дают одинаковый результат.

- Документация должна обновляться одновременно с кодом.

# Работа с Git



Обычный цикл разработки:



1. git status

2. git add

3. git commit

4. git push



Не использовать force push без серьёзной причины.



Не удалять историю проекта.



Каждый законченный этап должен иметь отдельный коммит.



---



# Работа с пользователем



Пользователь предпочитает разработку маленькими шагами.



Правила:



- давать одну проверяемую команду за раз;

- ждать вывод терминала;

- не предполагать успешность выполнения без проверки;

- объяснять решения простым языком;

- сначала получить работающий результат, потом заниматься улучшениями.
